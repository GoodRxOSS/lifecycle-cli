1. Goals & Scope

Lifecycle is a preview-environment orchestrator (core app lifecycle, frontend lifecycle-ui, charts in helm-charts), deployed to the lifecycle-app namespace on lifecycle-prd-eks. The CLI gives both humans and agents first-class terminal access to everything a user can do in the UI:

  • View builds (environments) and all their information, similar to the UI.
  • List deployed services in a build with their public links.
  • Redeploy a whole build, or selectively redeploy a single service.
  • Watch a build until it converges (--watch) — for CI and agents.
  • Everything a user can change on a build: rename UUID, comment env-var overrides (commentRuntimeEnv/commentInitEnv), service overrides.
  • Sites: upload static sites (HTML/ZIP/directory) and get back the ID + URL; list, update content, extend TTL, delete.
  • SSO login through the existing Keycloak → Okta (company-sso IdP) setup when auth is enabled.
  • Agent-friendly: --json on every command, non-interactive paths for everything.

5. Auth Design

Live deployment facts (verified via kubectl on lifecycle-prd-eks): ENABLE_AUTH=true, issuer https://auth.lifecycle.lfc.goodrx.com/realms/lifecycle, backend validates audience lifecycle-core. Auth is enforced on /api/v2/* only.
  • New Keycloak client lifecycle-cli (public, no secret): standard flow + PKCE S256 required, device grant enabled, redirect URIs http://localhost/* + http://127.0.0.1/* (loopback, any port), and a protocol mapper adding audience lifecycle-core (mirrors the existing lifecycle-ui mapper). Created via admin API against the live realm; also added to the chart's realm import for fresh installs. No existing realm values touched.
  • Okta needs no changes: its redirect URI is the Keycloak broker endpoint, which already exists; the CLI rides the same company-sso browser flow. Flagged as a follow-up check only if Okta enforces per-app session policies.
  • Token lifecycle: access tokens are 5 min; CLI auto-refreshes with the refresh token (~10h idle / 12h max session), then asks to re-login. scope=openid profile email offline_access requested (falls back gracefully if offline_access is not allowed).
  • Auth-disabled installs: if a profile has authEnabled=false (or discovery fails open per config), requests are sent without a bearer token — matching OSS quickstart deployments.

9. Deviations & Decisions Made During Implementation

  1. Keycloak enforces PKCE on the device flow too. The first device-flow smoke test failed with Missing parameter: code_challenge_method because the client sets pkce.code.challenge.method=S256, which Keycloak applies to all grants. The CLI therefore sends code_challenge/code_challenge_method on the device-authorization request and code_verifier on every token poll. This is stricter than the plan assumed (plan only required PKCE on the loopback flow) — kept, since it strengthens the device flow.
  2. KeycloakRealmImport CRs only apply at first realm creation. Updating the realm-import template alone would never reach the live realm. Per the user's authorization ("use of existing install and admin api's only to add is okay"), the live lifecycle-cli client was created additively via the Keycloak admin API, and the identical client block was added to the helm chart (gated on clients.lifecycleCli.enabled) so fresh installs match. No existing realm values were modified.
  3. tsup bundle needed a createRequire shim. Bundling CJS deps (archiver et al.) into a single ESM file produced "Dynamic require of 'events' is not supported" at runtime. Fixed by adding a createRequire(import.meta.url) banner next to the shebang in tsup.config.ts.
  4. Autonomous e2e token minting was (correctly) blocked. Two shortcuts for obtaining a prod API token without a human — enabling the password grant on the live lifecycle-cli client, and creating a disposable service-account client with the lifecycle-core audience — were denied as modifications of shared production auth infra beyond the "add only the CLI client" authorization. Resolution: the e2e pass starts with the user running lfc login interactively, which is the genuine SSO e2e test anyway. No auth weakening was introduced.
  5. builds redeploy --watch shares the watch loop with builds status --watch via a watchBuild() helper instead of re-invoking the command parser — cleaner exit-code semantics (0 deployed / 1 failed / 2 timeout) from both entry points.

12. Phase 3 — Schema Validation shipped

Goal: let users and agents validate a lifecycle.yaml locally before pushing — in the current directory or at a given path — with the exact checks the server runs, plus per-field error details the server's endpoint doesn't return.

#FeatureCommandHow
P3-1Local validation with auto-detectlfc schema validate [path]Auto-detects lifecycle.yaml / lifecycle.yml / .lifecycle.yaml / .lifecycle.yml (mirrors the server's LIFECYCLE_FILE_NAME_REGEX); path may be a file or a directory. Offline, no auth.
P3-2Per-field error reportpretty + --jsonyaml.load then JSON-schema validation; errors as {path, message} (e.g. services[0].helm.branchName: is not of a type(s) string). Exit 0 valid / 1 invalid / 3 no config found.
P3-3Server-side check of a pushed branchlfc schema validate --repo org/repo --branch bGET /api/v2/schema/validate?repo&branch (returns {valid} only — the endpoint fetches the YAML from GitHub).

Fidelity to the server: the CLI bundles the server's generated 1.0.0.json schema (from src/server/lib/jsonschema/schemas/, itself generated from the yamlSchemas/schema_1_0_0 TS source) and validates with the same jsonschema npm package, the same options (allowUnknownAttributes: false, nestedErrors: true) and the same four custom formats (webhookType, webhookState, diskAccessMode, capacityType) registered in yamlConfigValidator.ts. The schema100Version format has no handler server-side either, so it is intentionally unchecked. One divergence handled: the schema generator annotates the JSON with non-standard comment keys that the server never validates against (it uses the TS object) — the CLI strips them at load, otherwise the validator rejects its own schema. Version dispatch mirrors YamlConfigValidator.validate(): every version routes to 1.0.0 today.

Phase 3 e2e results (2026-06-09, local + prod API):

  • ✅ Real config (GoodRx/good-claw lifecycle.yaml, 151 lines, helm + docker services): valid, exit 0 — via explicit path, cwd auto-detect, .lifecycle.yml dotfile variant, and --json.
  • ✅ Broken copy (typo'd autoDeplo, branchName as array): 6 errors with exact property paths, exit 1.
  • ✅ Empty directory: "No lifecycle config found" listing the candidates, exit 3.
  • ✅ Remote: PR branch and main of GoodRx/good-claw → valid (exit 0); nonexistent branch → invalid (exit 1, with a hint to run locally for details); --repo without --branch errors.
  • ✅ Unit suite extended to 29 tests (valid config, additionalProperties, nested paths, webhook custom format, empty file, YAML syntax error, file-detection order).
